 EXECUTIVE SUMMARY
================================================================================
This document exists to remove EVERY judgment call from the UI-rebuild
process. The 3 reference images show 9 unique app screens for a music-
streaming product ("Sound Moves" on the onboarding screen, "RikoMusic"/
"VibePlay" as the two engineering codebases it will be built into). Every
color, spacing value, type style, component behavior, animation, and screen
layout visible in those images has been measured, named as a reusable token
or component, and written down below — and every place where the source
images were ambiguous, cropped, inconsistent with each other, or simply
silent (loading states, error states) has been resolved with a single final
decision in Section 9, so nobody building from this document ever has to
guess or wait on a design review to keep moving.

WHAT "ENTERPRISE" MEANS IN THIS EDITION:
   1. Nothing is tribal knowledge. Every role involved (design, Android/
      Compose engineering, React Native engineering, QA, accessibility)
      has a defined responsibility in Part A, Section A1.
   2. Nothing ships un-reviewed. Every phase of the build has an explicit
      entry condition, exit condition, and required sign-off role — Part A,
      Section A2.
   3. Nothing drifts silently. If a decision in Section 9 ever needs to
      change, there is a defined Change Control process — Part A, Section
      A4 — instead of someone quietly editing a component and the rest of
      the team finding out in QA.
   4. Nothing is "eyeballed" at review time. The QA checklist in Part B,
      Section 8 is backed by a numeric, tool-verifiable pixel-diff
      threshold in Part C, Section C4 — pass/fail is a number, not a
      feeling.
   5. Nothing is undiscoverable. Part C, Section C1 is a single
      traceability matrix mapping all 9 screens to every component, token
      group, and QA checklist item they depend on, so a change's blast
      radius is always known before it's made.

HOW TO USE THIS DOCUMENT TOGETHER WITH THE SLIDE DECK
   - This .txt file is the SOURCE OF TRUTH — every exact number, hex value,
     and finalized decision lives here and only here.
   - The companion .pptx is the VISUAL WALKTHROUGH — it puts the actual
     cropped reference screenshots next to the design tokens and component
     rules so a reader who is not fluent in reading a written spec (a
     junior developer, a freelancer, a stakeholder approving the look) can
     still confirm, at a glance, "yes, that is the UI we are building,"
     without reading a single paragraph of this document.
   - If the two ever appear to disagree, THIS DOCUMENT WINS — the deck is a
     presentation layer generated from it, not an independent source.

 A2. STAGE-GATE DELIVERY MODEL
================================================================================
Part B, Section 7 already defines WHAT to build in each phase (Phase 0
through Phase 8). This section adds the ENTERPRISE CONTROL LAYER around it:
every phase gets an explicit entry gate, exit gate, and the role that must
sign off before the next phase is allowed to start. Do not begin phase N+1
work before phase N's exit gate is signed — this is the single highest-
leverage rule in this document for preventing rework, because every later
phase in Section 7 explicitly depends on tokens/components built in an
earlier one.

   PHASE 0 — Design Tokens
      Entry gate   : Section 1 read in full by DL + both engineering leads.
      Exit gate    : Color.kt/Type.kt/Shape.kt/Dimens.kt (Compose) AND
                     tokens.ts (RN) both compile/import cleanly and expose
                     every named token in Section 1's tables — zero raw hex/
                     px values allowed anywhere outside these files from
                     this point forward.
      Sign-off     : DL (design fidelity) + CE + RNE (both tracks present).

   PHASE 1 — Atomic Components
      Entry gate   : Phase 0 signed off.
      Exit gate    : Every component in Section 2 with no child components
                     (IconButton, PrimaryButton, SecondaryButton,
                     ToggleSwitch, SortDropdownChip, FilterTabPill) has a
                     Preview/Storybook entry for every state listed in its
                     spec, matching Section 2's states 1:1.
      Sign-off     : DL.

   PHASE 2 — Composite Components
      Entry gate   : Phase 1 signed off.
      Exit gate    : Every remaining Section 2 component (2.9-2.22) built
                     using ONLY Phase-1 primitives + design tokens; visually
                     compared against its source screen crop (see Part C,
                     C4) at ≥95% pixel match before moving on.
      Sign-off     : DL + QA.

   PHASE 3 — Static Screen Assembly
      Entry gate   : Phase 2 signed off; all 22 Section-2 components exist.
      Exit gate    : All 9 screens in Section 3 assembled with the EXACT
                     sample data strings given in each screen's spec (not
                     placeholder Lorem Ipsum — real sample data is required
                     because Part C, C4's pixel-diff QA depends on matching
                     text length/wrapping to the reference).
      Sign-off     : DL + QA (full Section 8 checklist run once here).

   PHASE 4 — Navigation Wiring
      Entry gate   : Phase 3 signed off.
      Exit gate    : Section 4's navigation map fully wired on the track(s)
                     in scope; every transition in Section 5.2 present and
                     using the correct token duration/easing.
      Sign-off     : CE and/or RNE (whichever track is in scope) + QA.

   PHASE 5 — Data Layer
      Entry gate   : Phase 4 signed off.
      Exit gate    : Real playback state drives TransportControlBar/
                     WaveformVisualizer; mock data fully replaced by live
                     data sources without any visual regression vs. Phase 3
                     (re-run Section 8 checklist).
      Sign-off     : CE and/or RNE + QA.

   PHASE 6 — Motion Polish
      Entry gate   : Phase 5 signed off.
      Exit gate    : All remaining Section 5 items (5.2 through 5.10)
                     implemented in the listed priority order.
      Sign-off     : DL + QA.

   PHASE 7 — Platform Polish
      Entry gate   : Phase 6 signed off.
      Exit gate    : Every item in Section 7's "Phase 7" list complete, PLUS
                     Part C Section C5 (accessibility) fully audited and
                     passing.
      Sign-off     : AX + QA.

   PHASE 8 — Final QA & Sign-Off
      Entry gate   : Phase 7 signed off.
      Exit gate    : Section 8 checklist passes on every one of the 9
                     screens AND the numeric thresholds in Part C, C4 are
                     met, recorded on the Part C, C9 Acceptance Certificate.
      Sign-off     : QA (executes) -> PO + DL + AX co-sign the certificate.
                     REL then owns the release itself.

================================================================================
 A4. CHANGE CONTROL PROCESS
================================================================================
Every decision in Part B, Section 9 is marked FINALIZED — meaning: build
against it now, with no further sign-off needed to START building. This is
what makes the document actionable on day one. It does NOT mean a decision
can never be revisited; it means revisiting one is a deliberate, tracked
event, not a quiet edit. Follow this process if a finalized decision needs
to change (e.g. a real Figma source file surfaces and disagrees with a
best-match value, or a stakeholder rejects a Section-9 call after seeing it
built):
   1. RAISE — Open a change note referencing the exact decision ID (e.g.
      "D5") or token name (e.g. "accent-magenta"). State what's changing
      and why.
   2. IMPACT ANALYSIS — Use the Part C, Section C1 Traceability Matrix to
      list every screen/component the change touches. A token change
      (Part A never allows a one-off local override — Phase 0's exit gate
      forbids it) will typically cascade to multiple screens; that is
      expected and is exactly why the matrix exists.
   3. APPROVE — Per the Section A1 RACI: DL is Accountable for design-
      token/component changes; PO is Accountable for anything touching
      product scope or a Section-9 UX decision (like D5's transport-button
      order or D13's mini-player addition).
   4. VERSION — Bump this document's version number (see Document Control)
      and add a Revision History row describing exactly what changed and
      why. Never edit a past revision-history row.
   5. RE-BASELINE — Update the Part C, C4 visual-regression baseline images
      for every impacted screen BEFORE merging the change, so the next QA
      run compares against the new intended truth, not the old one.
   6. RE-CERTIFY — Any screen touched by the change must re-pass Section 8
      + Part C, C4 and get a fresh line on the Part C, C9 certificate.

DOCUMENT PURPOSE
--------------------------------------------------------------------------------
This document is a complete, standalone build specification for recreating the
music-streaming app UI shown in the 3 reference images supplied
(1000226926.webp, 1000226927.png, 1000226925.webp). It is written so that a
developer or an AI coding agent (e.g. Claude Code) can follow it top-to-bottom
with ZERO additional creative interpretation and produce a pixel-accurate,
production-ready UI — same layout, same colors, same type, same spacing, same
motion.

SOURCE OF TRUTH & METHODOLOGY (read this first)
--------------------------------------------------------------------------------
- All colors in this document were extracted by programmatically sampling
  pixel RGB values directly from the 3 reference images (not guessed).
  Every hex value below carries an implicit +/- 3% tolerance because the
  source files are compressed marketing renders (700-752px wide WEBP/PNG),
  not raw design files.
- All spacing/sizing values are DERIVED measurements snapped to a standard
  8-point spacing grid (see 1.1). This is standard professional practice:
  a designer measuring a screenshot always rounds to the grid the original
  designer almost certainly used. Treat these as the authoritative build
  values unless a Figma/XD source file exists — if one exists, that file
  wins and this document should be updated to match it.
- Font family could NOT be verified with certainty from a raster image
  (font identification from pixels is inherently a best-match exercise).
  A confident best-match + safe fallback is finalized in 1.3/Section 9 —
  build with it directly; only revisit if an original design source
  later surfaces and disagrees.
- Reference artboard = 390 x 844 dp (iOS "iPhone 14/13/12" logical point
  size — this is the frame size the mockups were clearly built at, given
  the Dynamic Island + status bar proportions visible in every screen).
  All dp values below assume this frame. If your target is Android,
  treat dp = dp (1:1, same unit system). If your target is React Native,
  treat dp = React Native's density-independent "px" (1:1, same thing).

HOW TO USE THIS DOCUMENT (execution order)
--------------------------------------------------------------------------------
   1. Read Section 1 (Design Foundation) fully and encode it as code FIRST —
      colors.kt/xml, typography.kt, spacing.kt, shape.kt (or theme.ts/tokens.ts
      for RN). Nothing in Section 2/3 should hardcode a raw hex or px value —
      everything must reference a token from Section 1.
   2. Build every component in Section 2 (Global Component Library) as an
      isolated, reusable, preview-able unit BEFORE touching any screen.
   3. Assemble screens in Section 3 using ONLY the components from Section 2.
      Do not create one-off, screen-specific variants of a shared component.
   4. Wire navigation per Section 4.
   5. Apply motion per Section 5.
   6. Run the QA checklist in Section 8 against the 3 original reference
      images, screen by screen, before calling any screen "done".
   7. Section 9 lists every ambiguity found in the source images together
      with the FINAL decision made for each. These are resolved — build
      directly against them, no further sign-off needed.

1.2  COLOR SYSTEM
--------------------------------------------------------------------------------
   A) BACKGROUND — "App Canvas" (used on every screen except the two screens
      that are dominated by a full-bleed photo: Onboarding & Now Playing hero
      photo area)

      This is NOT a flat color. It is a layered dark background:
        Layer 1 — Base vertical linear gradient (top -> bottom):
            0%   #0A0A52   (deep indigo-navy)
            30%  #060750   (indigo)
            60%  #04041D   (near-black navy)
            100% #020210   (almost pure black, slight blue cast)
        Layer 2 — One or two soft ambient "glow" blobs on top of Layer 1:
            Color: #6C3CE9 (violet) at 10-14% opacity
            Shape: circle/ellipse, diameter ~60% of screen width
            Blur : Gaussian blur radius ~120 dp (heavy, soft glow — no hard
                   edge should ever be visible)
            Position: varies per screen — generally upper-right-of-center
                   or center, NEVER perfectly symmetric (feels organic).
        Layer 3 — A second, darker "shadow" blob (near-black, #000000 at
            ~30-40% opacity, blur ~150dp) is layered lower-right on list-
            heavy screens (Favourites, Playlist) to add depth/vignette.

      IMPLEMENTATION OPTIONS (pick one; both are valid):
        Option A (scalable/code-based): Build as a Compose Brush /
            RN LinearGradient + 2 absolutely-positioned blurred Views/Boxes
            behind content. Cheapest to maintain, scales to any screen size.
        Option B (pixel-perfect): Export the background as one static
            1x/2x/3x PNG/WebP asset per screen (or one shared asset if the
            blobs are identical across screens) and set as a full-bleed
            background image. Guarantees exact visual match.
        RECOMMENDATION: Option A for engineering velocity; fall back to
            Option B only if a design review rejects the code-based result.

   B) PRIMARY BRAND GRADIENT — "Aurora" (the single accent used for every
      primary/active/selected element across the entire app: primary
      buttons, active tab pill, active bottom-nav icon, toggle-on state,
      "+" add button, progress/selection indicators)
            Stop 0%   : #8A2BF0   (Violet)
            Stop 100% : #C92CEE   (Magenta / Fuchsia)
            Angle     : 90° (left->right) as the default; several components
                        in the reference use it mirrored at 270°
                        (right->left) — see each component's spec in
                        Section 2 for which direction to use. Implement as

================================================================================
 SECTION 5 — MOTION & ANIMATION SPECIFICATION
================================================================================

5.1  MOTION TOKENS (define once, reuse everywhere)
--------------------------------------------------------------------------------
      duration-fast     100 ms   -> press/tap feedback
      duration-base     200 ms   -> simple fades, color/opacity changes
      duration-medium   300 ms   -> pill/tab morphs, toggle slide
      duration-slow     400 ms   -> screen transitions, shared-element moves
      easing-standard   cubic-bezier(0.2, 0.0, 0, 1.0)   (Material
                        "standard" curve — decelerate) — use for anything
                        entering/appearing
      easing-emphasized cubic-bezier(0.3, 0.0, 0.8, 0.15) enter /
                        cubic-bezier(0.05,0.7,0.1,1.0) exit — use for
                        shared-element/hero transitions (album art)
      spring-snappy     stiffness ~300, damping ~26 (Compose/RN Reanimated
                        spring params) -> nav active-indicator, toggle
                        thumb, like-button burst

5.2  SCREEN TRANSITIONS
--------------------------------------------------------------------------------
      Tab switches (Home/Favourites/Library/Settings): instant cross-fade,
         duration-base (200ms), no slide — these are peer destinations.
      Push transitions (e.g. Playlist -> Playlist Detail, any row -> Now
         Playing): slide-in from right + fade, duration-slow (400ms),
         easing-standard; previous screen slides left ~30% width + dims
         to 70% opacity (standard iOS-style push).
      Now Playing entry specifically: implement as a SHARED ELEMENT
         transition — the tapped row's square thumbnail morphs (position
         + size + corner-radius 12dp->140dp/circle) into the destination's
         CircularHeroAlbumArt, duration-slow, easing-emphasized. This is
         the single highest-impact animation in the whole app — prioritize
         it.
      Onboarding -> Home: fade + slight scale (0.98->1.0), duration-slow.

5.3  BOTTOM NAV SELECTION
--------------------------------------------------------------------------------
      The active-state filled circle behind the icon animates its
      position using spring-snappy when switching tabs (do NOT just swap
      opacity — physically slide the circle from the old tab's position
      to the new one, ~180-220ms perceived duration via spring). Icon
      color cross-fades (glass/60%-white -> solid white) over duration-fast
      in sync with the circle's arrival. Icon may also do a subtle scale
      pulse (1.0 -> 1.15 -> 1.0) over 250ms on selection for extra
      tactility.

5.4  BUTTON / TAP FEEDBACK (all buttons, all icon buttons)
--------------------------------------------------------------------------------
      On press-down: scale to 0.96, duration-fast, easing-standard.
      On release: scale back to 1.0, duration-fast.
      Primary gradient buttons additionally darken ~8% during the press
      (overlay black at 8% opacity) for tactile depth.

5.5  HEART / LIKE MICRO-INTERACTION
--------------------------------------------------------------------------------
      On like (outline -> filled): icon scales 1.0 -> 1.3 -> 1.0 over
      300ms (spring-snappy) while cross-fading outline->filled at the
      midpoint; optionally emit 4-6 small particle dots in the accent
      colors that fade+fly outward over 400ms for extra delight (nice-to-
      have, not required for MVP).

5.6  TOGGLE SWITCH
--------------------------------------------------------------------------------
      Thumb slides left<->right over duration-medium (300ms) using
      spring-snappy; track color cross-fades (off-fill -> gradient)
      simultaneously over duration-base.

5.7  TAB PILL / FILTER SWITCH
--------------------------------------------------------------------------------
      When a FilterTabPill becomes active, its background morphs from
      glass-fill to Primary Brand Gradient over duration-base with a
      simultaneous text-color cross-fade. If pills reflow width, animate
      width changes with spring-snappy. Auto-scroll the tab row so the
      newly active pill is fully visible (duration-medium, easing-
      standard).

5.8  WAVEFORM / PLAYBACK PROGRESS
--------------------------------------------------------------------------------
      While PLAYING: bars in the "played" zone stay static height (they
      represent the track's fixed amplitude shape, not a live equalizer)
      but the "played vs unplayed" color boundary advances continuously,
      frame-synced to actual playback position (no easing — this is a
      direct 1:1 mapping to audio currentTime/duration).
      OPTIONAL premium enhancement: while playing, animate 2-3 bars near
      the current playhead with a subtle live "bounce" (height *0.9-1.1,
      random/pseudo-random per-frame, 150-250ms per bounce cycle) to sell
      the sense of a live visualizer — pause this animation immediately
      on pause/seek.
      Drag-to-seek: thumb/played-boundary follows the finger 1:1, no
      inertia; on release, commit the seek with duration-fast confirm.

5.9  LIST ENTRANCE
--------------------------------------------------------------------------------
      On first screen load, stagger TrackListRow/ArtistRow/MoodGridCard
      items with a fade (0->1 opacity) + slide-up (12dp->0dp) over
      duration-base per item, with a 30-40ms stagger delay between
      consecutive items (cap the stagger so it never exceeds ~6 visible
      items' worth of delay — items further down should NOT wait for the
      whole stagger chain, fade in immediately once scrolled into view
      instead).

5.10 LOADING / SKELETON STATES
--------------------------------------------------------------------------------
      Not present in the static reference images (only "happy path" data
      is shown). FINALIZED approach for production (Section 9): use a
      shimmer sweep (light band at 15% white opacity moving left->right,
      1200ms loop, linear) over glass-fill-colored placeholder shapes
      matching each component's exact geometry (thumbnail squares,
      text-line bars at Body-Bold/Caption heights).

 C2. DESIGN-TOKEN GOVERNANCE & VERSIONING POLICY
================================================================================
Treat Section 1 tokens as a VERSIONED PACKAGE, not a file anyone edits
freely — this is what stops the Compose and RN tracks from drifting apart
(Risk R2 in Part A, Section A5).

   RECOMMENDED SOURCE-OF-TRUTH FORMAT
      Maintain ONE platform-agnostic file, e.g. /design-tokens/tokens.json,
      that both Color.kt/Type.kt/Dimens.kt (Compose) and tokens.ts (RN) are
      GENERATED from (by hand-sync on a small team, or by a build script on
      a larger one) — never hand-author the same value twice in two
      languages. Example shape (illustrative, not exhaustive):

          {
            "color": {
              "bg-gradient-top": "#0A0A52",
              "bg-gradient-bottom": "#020210",
              "accent-violet": "#8A2BF0",
              "accent-magenta": "#C92CEE",
              "text-primary": { "hex": "#FFFFFF", "opacity": 1.0 },
              "text-secondary": { "hex": "#FFFFFF", "opacity": 0.6 }
            },
            "spacing": { "space-1": 4, "space-5": 20, "space-6": 24 },
            "radius": { "radius-xs": 8, "radius-sm": 12, "radius-full": 9999 },
            "type": {
              "button-label": { "size": 15, "weight": 600, "lineHeight": 20,
                                  "letterSpacing": 0.2 }
            }
          }

   VERSION NUMBER RULE (semver-style, applies to the token package only,
   independent of this document's own v2.0 revision number in Document
   Control):
      MAJOR (x.0.0) — any token's rendered VALUE changes (a hex shifts, a
         spacing value changes) — this can silently break visual QA on
         every screen listed against that token in Section C1, so it
         requires full Change Control (Part A, A4) and a full Section 8 +
         C4 re-run on every affected screen.
      MINOR (0.x.0) — a NEW token is added without changing any existing
         one (e.g. a token needed for a screen outside the original 9,
         added later) — no re-baseline required for existing screens.
      PATCH (0.0.x) — a token's internal NAME/comment/organization changes
         with no rendered-value change — no functional re-test required,
         but update this document's token tables to match.
   Keep a CHANGELOG.md next to tokens.json recording every bump with the
   Part A, A4 change-note reference.

 C4. VISUAL REGRESSION & TESTING STRATEGY
================================================================================
This section turns Part B Section 8's checklist from a subjective look-over
into a numbers-based pass/fail gate.

   BASELINE IMAGES
      Crop each of the 9 screens directly out of the ORIGINAL REF-1/2/3
      files (never from a rendering of a previous build — see Risk R7,
      Part A) at the phone-frame boundary, save as the baseline for that
      screen at 1x/2x/3x. Store under /qa/baselines/<screen-name>.png.

   TOOLING
      [COMPOSE] Paparazzi (JVM screenshot testing, no emulator needed) or
         Shot (device/emulator-based) — either compares a rendered
         Composable directly against a stored baseline PNG.
      [RN] react-native-view-shot to capture a rendered screen + pixelmatch
         (or a hosted service like Chromatic/Percy if the team already
         uses one) to diff against the baseline.
      Both tracks feed the SAME baseline images from /qa/baselines/ — this
      is what actually prevents Risk R2 (platform divergence) rather than
      just documenting the risk.

   NUMERIC THRESHOLD (operationalizes the brief's "1000000% pixel-accurate"
   request into something a CI job can actually check)
      PASS  : ≤ 1.0% mismatched pixels for the screen, EXCLUDING the masked
              region below.
      WARN  : 1.0%-2.5% — allowed to merge with QA sign-off + a written
              note of what's different and why (e.g. real dynamic data vs.
              the fixed sample strings from Section 3).
      FAIL  : > 2.5% — blocks merge; must be fixed or go through Part A,
              Section A4 Change Control if the difference is an intentional
              deviation from the reference.
      MASKED REGION: the system status bar's clock/battery/signal glyphs
              (top ~44dp) are excluded from the diff — these are OS-drawn,
              not app content, and will legitimately differ (real time vs.
              the reference's fixed "9:41" mock).

   CI GATE
      Wire the visual-regression job to run on every PR touching
      `ui/components`, `ui/screens`, `theme`, or `tokens.ts`. A FAIL blocks
      merge. A WARN requires an explicit QA approval comment on the PR.

   OTHER TEST LAYERS (standard engineering hygiene, not unique to this
   spec, listed for completeness)
      - Unit tests for any pure logic (duration formatting, progress-
        percentage calculation for WaveformVisualizer, RTL-aware layout
        math per Section C7).
      - Component preview/story coverage per Phase 1/2 exit gates
        (Part A, Section A2) — every state listed in Section 2 must have a
        preview, which doubles as living documentation.
      - Manual accessibility pass per Section C5 (automated contrast checks
        catch color; they don't catch screen-reader label quality).

 C5. ACCESSIBILITY COMPLIANCE APPENDIX (WCAG 2.1 AA)
================================================================================
Contrast ratios below were calculated (relative-luminance method, WCAG 2.1
formula) directly from the Section 1.2 hex/opacity values against BOTH ends
of the background gradient (the lightest stop, bg-gradient-top #0A0A52, is
the worst case for any dark-on-dark risk; the darkest stop, bg-gradient-
bottom #020210, is included too since content scrolls across the whole
gradient).

   TEXT TOKEN vs BACKGROUND               CONTRAST     AA NORMAL TEXT   AA LARGE/BOLD TEXT
   (rendered/composited color)            RATIO        (4.5:1 needed)   (3:1 needed)
   -------------------------------------  -----------  ---------------  -------------------
   text-primary (100% white) vs top       17.82 : 1    PASS             PASS
   text-primary (100% white) vs bottom    20.61 : 1    PASS             PASS
   text-secondary (60% white) vs top       6.76 : 1    PASS             PASS
   text-secondary (60% white) vs bottom    7.36 : 1    PASS             PASS
   text-tertiary (38% white) vs top        3.35 : 1    FAIL             PASS (borderline)
   text-tertiary (38% white) vs bottom     3.41 : 1    FAIL             PASS (borderline)
   text-on-accent (white) vs accent-violet 5.70 : 1    PASS             PASS
   text-on-accent (white) vs accent-magenta 4.14 : 1   FAIL (normal)    PASS

   FINDINGS & REQUIRED ACTIONS
      1. text-secondary (60% white) — Section 1.2-D's own note asked
         reviewers to "spot-check... bump to 65-70% if any screen fails."
         The calculation above shows 60% white PASSES AA comfortably
         (6.76-7.36:1) against both gradient stops as specified — NO bump
         is required. Keep 60% as specified; this finding closes out that
         open question from the original spec.
      2. text-tertiary (38% white) — FAILS AA for normal body text
         (3.35-3.41:1 vs the required 4.5:1), though it clears the lower
         3:1 bar used for large/bold text and non-text UI components. The
         spec already scopes this token to "disabled / least-important
         meta (rarely used)" — CONFIRM every real usage is either (a) on
         large/bold text only, or (b) purely decorative/disabled-state
         (which WCAG exempts from the 4.5:1 rule). If any future screen
         needs REAL informational text at this tier, raise the opacity to
         ≥48% (recalculated to pass 4.5:1 at 48-50%) via Part A, A4 Change
         Control rather than using text-tertiary as-is.
      3. Button-Label text-on-accent vs accent-magenta (4.14:1) — FAILS the
         4.5:1 normal-text bar but PASSES the 3:1 large/bold-text bar.
         Button-Label is 15sp SemiBold (Section 1.3), which qualifies as
         "large/bold" under WCAG's ≥14pt-bold threshold — treat as PASS,
         but do not shrink Button-Label below 14sp/pt at any dynamic-type
         scale, or this combination will drop below compliance.

   TAP TARGET AUDIT (WCAG 2.5.5 / platform HIG minimum 44x44dp/pt)
      Every icon-only control in Section 1.7 already specifies a hit-area
      of 44x44 or larger EXCEPT: MENU_ONLY kebab (32x32 — Section 2.11c)
      and the toggle switch thumb region. ACTION: keep the visible kebab
      glyph small (18dp) as specified, but pad its actual touch target to
      44x44 in code (a larger invisible hit-slop), exactly as Section 7,
      Phase 7 already instructs — this appendix formalizes it as a
      required, auditable check, not an optional nicety.

   SCREEN-READER LABELS
      Every icon-only IconButton (search, heart, bell, back-chevron, kebab,
      play-in-circle) requires an explicit accessibility label/content-
      description — see the Section 1.4 Icon Inventory for the semantic
      name to use as the base of each label (e.g. icon "heart (outline)" ->
      label "Add to favourites" / "heart (filled)" -> "Remove from
      favourites", state-dependent).

   DYNAMIC TYPE / FONT SCALING
      All type-scale values in Section 1.3 must respond to the OS-level
      text-scaling setting (Compose: sp units inherently scale; RN:
      allowFontScaling should NOT be disabled). Re-verify Section C1's
      per-screen list-row heights (76dp) still fit two lines of text
      without clipping at the largest supported OS text-scale step (test
      at 130% minimum).

 C6. PERFORMANCE BUDGET
================================================================================
   - List virtualization is REQUIRED for every TrackListRow/ArtistRow list
     (LazyColumn on Compose, FlatList/FlashList on RN) — never a raw
     map()-rendered scroll view, given lists like "170 favourites."
   - Target 60fps for all Section 5 motion; the 5.9 list-entrance stagger
     must degrade gracefully (skip the stagger, keep the fade) on lower-
     end devices rather than drop frames.
   - Image loading: use a caching image loader (Coil on Compose, expo-
     image or FastImage on RN) for every thumbnail/artist-photo/mood-card
     image; prefetch the next screen's above-the-fold images during the
     Section 5.2 screen-transition animation, not after it completes.
   - Cold start budget: Onboarding screen (3.1) interactive within 2s on a
     mid-tier device — it is a full-bleed photo background, so ship it as
     a pre-optimized asset per Section 6, not a runtime-fetched image.
   - Ambient background (Section 1.2-A): if Option A (code-based blur) is
     chosen, verify blur-radius 120-150dp does not cause jank on low-end
     GPUs during scroll; fall back to Option B (static exported asset) per
     device-tier if profiling shows a regression.

================================================================================
 C7. INTERNATIONALIZATION & RTL NOTES
================================================================================
   - If the product ships in an RTL locale (Arabic, Hebrew, Urdu, etc.):
     mirror horizontal layouts (AppBar icon order, TrackListRow
     thumbnail-left/trailing-right becomes thumbnail-right/trailing-left,
     BottomNavBar item order) using the platform's native RTL layout
     direction support (Compose LayoutDirection, RN I18nManager) rather
     than hand-flipping each screen.
   - Icons that encode DIRECTION must flip in RTL (chevron-left/right,
     back arrow). Icons that do NOT encode direction must NOT flip:
     play-triangle, pause bars, shuffle, heart, gear, bell, search — these
     keep their Section 1.4 orientation in every locale. The Section 3.7
     transport-bar's non-standard order (D5) is a FIXED VISUAL DECISION,
     not a directional icon — do not let an automatic RTL mirror reorder
     it; explicitly pin its icon sequence regardless of layout direction.
   - String-length tolerance: sample strings in Section 3 (e.g. "Add New
     Playlist", "Experience Music Without Limits") are short-to-medium
     English phrases. Translated strings (German, Bengali, etc.) commonly
     run 20-35% longer — verify Button-Label and Title-M containers (e.g.
     PromoBannerCard heading, PrimaryButton label) truncate gracefully
     (ellipsis, max 2 lines) rather than overflowing their Section 1.7
     component bounds.
